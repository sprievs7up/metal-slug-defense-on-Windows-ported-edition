## 2. 周期校验

### 2.1 定义

- 语义校验 h：与 N0–N4 相同（`BattleMain +0x48`、宿主随机数、双方 AP / 据点等级 / 10 格冷却、各单位 UnitID / 实例 / 坐标 / 生命）。
- 深度校验 d：N4 的各区域（BattleMain、双方控制器、各单位、对象管理器去指针后的字节）之后，再串接**单位数据表**（BattleInfo 数据行，每行 0x390 字节）的 CRC32。
  当前本体内容为 1044 行、952,128 字节；数据表在主菜单与整场战斗中不变（`runs/probe_layout/layout.json`），被内存修改时 d 随之不同。
- 双方控制器的 0x440 字节包含 10 个出兵格信息（控制器 +12 起，每格 28 字节：+0 出兵 AP、+0xc 可用、+0x10 UnitID、+0x18 冷却），控制器 +0x404 为 AP（单精度浮点）。
- 新参照（`runs/ref1`、`ref2`、`ref_hp`）与 N4 参照相比：h 在全部校验点上相同，结束帧相同（1603、2554）；d 因加入数据表而不同。模拟本身未改变。

### 2.2 传送（tag）与缺失判定

- 传送值 tag = BLAKE2b-64（`msd-netplay-checksum`、轮次、帧、**发送方一侧**、h、d）。接收方以本方的 h、d 按对方一侧计算后比较。
  对方只收到本方的 tag，不能把它原样发回冒充自己的值（原样发回必然不符，见第 5 节 x5）。
- 每个 TAGS 包携带最近 4 个已确认校验帧（每 30 帧一个），任一包送达即可比较；N4 每帧只发送一次、丢包即少比较一个点。
- 缺失（missing）：本方已确认帧超过对方最近一个校验帧 300 帧（10 秒）而对战尚未结束时判定为分歧。
  确认帧推进需要对方的输入，网络中断时双方的确认帧都停止，因此断网恢复不会误判（第 5 节 h3、local_pair 编号 3）。
- 一致的校验帧丢弃其快照（保留最近 4 个，用于对方在本方已一致的帧报告分歧时比较）；不一致或未比较的保留，最多保留 900 帧内的快照。

### 2.3 第 0 帧（开战前一刻）

ready 消息除第 0 帧校验值外，另带双方编队每个单位在本场等级下的实际数值摘要（`getUnitStatus` 与 `getUnitCreateParams` 的输出，含加载器倍率与覆盖补丁；BLAKE2b-64）。
不一致时双方拒绝（`frame0_mismatch`），差异列表按项列出“开战时状态校验值不同”或“开战时单位实际数值不同：P1 第 1 格 UnitID 3”，随后双方仍交换第 0 帧数据并写出分歧报告。
只修改原生倍率表（数据行不变）的改动不影响第 0 帧校验值，由单位摘要检出（第 5 节 x6）。

## 3. 分歧时的处理流程

1. 任一方检测到分歧（`session.desync`：`checksum` 或 `missing`），或收到对方的分歧通知（`match.peer_desync`），即停止推进对战（不再调用 `session.tick()`）。
2. 发送分歧通知 `desync`（种类、帧、由谁检测）与分歧数据 `desync_data`（可靠消息）：
   - 最近一致帧之后、至分歧帧为止本方保留的快照（最多 6 个，另含分歧帧本身）；
   - 这些帧之前一个校验间隔起的已确认双方输入；
   - 当前单位数据表逐行 CRC32。
   收到通知的一方以相同方式回送本方数据。每轮各发送一次。
3. 等待对方数据（最多 15 秒，期间只处理网络），以 `netplay_desync.safe_report`（`build_report` 的保护包装，生成失败时返回带错误说明的基本报告，不中断结束流程）生成分歧报告，保存为 `desync_r<轮>_f<帧>_<时间>.json`，并显示中文说明。
4. 结束会话（`session.end()`），LAB 合拢闸门回到准备界面（体面结束）；结果交换照常进行（outcome 记录不一致的帧）。
5. 第 0 帧不一致时，在拒绝之后执行第 2–3 步（种类 `frame0`），再结束会话。

N6 的游戏内联机循环按同一顺序实现，并向玩家显示报告的前几行（第 8 节）。

## 4. 分歧报告格式（`netplay_desync.build_report`，schema 1）

| 字段 | 内容 |
| --- | --- |
| `kind` | `checksum`（周期校验不同）、`missing`（对方校验值缺失）、`frame0`（开战时不同） |
| `frame` | 第一个不一致的帧：双方都有快照的帧中最早不一致者；没有共同快照时为检测到的帧 |
| `detected`、`last_match` | 双方各自检测到的帧与最近一致的帧 |
| `checksums` | 该帧双方的 h、d |
| `regions` | 不一致的区域，按 BattleMain、宿主随机数、P1 / P2 控制器、单位（按队伍与实例编号对齐；只在一方存在的单位单独列出）、对象管理器、单位数据表的顺序。每项含字段名与双方数值（`fields`，坐标与生命同时给出浮点值）、不同的字（`words`：偏移、双方数值；控制器偏移标注出兵格与字段，如“第 3 格 冷却”“AP”；每区域最多 12 个）与不同字的总数 |
| `table_rows` | 当前单位数据表中双方不同的行号（即 UnitID） |
| `inputs` | 双方记录的已确认输入的比较（比较帧数、不同的帧） |
| `flags` | `forged_checksum`：双方该帧状态相同而对方发来的 tag 与之不符 |
| `notes` | 第 0 帧差异列表等补充说明 |
| `text` | 中英文说明（每个区域一行，最多 12 行） |

示例（第 5 节 x1，加入方锁定本方 AP）：房主的报告为“对战状态不一致（周期校验值不同）：第 630 帧 / P2（对方）控制器：AP 140 / 0，1 个字不同”，加入方的报告从本方角度给出相同内容。

## 6. 回滚记录缺陷修正（N1 起存在，N5 发现）

- 现象：本机双客户端编号 2（单向 100 ms、丢包 2%）的第 2 轮（再战，地图 1055），加入方在约第 1200 帧报告 `Guest heap exhausted`。
  已同步运行目录中的 N4 版本在相同条件下同样复现（`runs/r2_heap_1055_n4dist_*`），属既有缺陷。
- 定位：单进程复现（`diag_heap.py`）：无回滚时连续两场正常；有回滚时第 2 场客体堆顶一直平稳（52.3 MiB），某一帧出现 `operator new(0xFFFFFFFF)`
  （`runs/diag_heap_rb2/huge_alloc.json`，调用位置 `_Znwj`），即对象状态已损坏、算出的长度为 −1。
- 原因：`GuestJournal.begin` 只复制“上次重置写入监视以来写过的页”。进程中的第一场会话开始时，这等于全部写过的页；但每次提交与恢复都会重置写入监视，
  因此同一进程的下一场会话（再战）开始时只复制两场之间写过的页，其余仍含有效内容的页在新的影子副本中为零。这些页在第二场中首次被改动的那一帧若被回滚，
  会被写回零，造成状态损坏。N4 的长时间与多轮测试未暴露此问题：t15 无回滚，t2、t14 的第 2 轮中受影响的页恰未在回滚窗口内首次改动。
- 修正：记录本进程迄今写过的全部页（每次取得写入监视结果时并入，各次会话共用），会话开始时全部复制到影子副本。第一场会话的行为不变；
  第二场起会话开始时与第一场相同地复制全部写过的页（r1 中两轮均约 62 MB，每场一次）。回放（N5.5）同样受益。
- 修正后：单进程三场与参照一致（第 5.4 节）；双进程 r1（第 5.2 节）两轮与参照一致。

## 7. 篡改检测的范围与限制

- 检出：战斗中修改己方数值（AP、生命、单位字段）、修改单位数据表、修改倍率等使编队单位实际数值不同（开战前检出）、伪造内容清单而实际内容不同、
  停止发送校验值、把对方的校验值原样发回。对战中的修改在下一个已确认的校验帧（每 30 帧）比较时检出，测试中第 600 帧开始修改、第 630 帧检出，双方随即结束本轮。
- 每个客户端都以自己的程序与数据、按双方输入模拟整场对战。对方修改程序只会改变对方自己看到的对局，不会改变本方的模拟；分歧检测的作用是让双方知道“看到的已不是同一场对战”并结束本轮、留下报告。
- 不能检出：修改过的客户端另行运行一份未修改的模拟来计算校验值（在点对点、无服务器裁决的结构下无法防止）；只改变画面而不影响模拟状态的修改；
  宏或辅助输入（与正常输入无法区分）。连接不加密（N4 第 8 节）。修改只发生在不参与比对的界面层时不会被检出，也不影响对局。
- 只修改了未出现在双方编队中的单位时，开战前不会检出（该单位不参与本场）；若该单位在战斗中由召唤等方式出现并影响状态，由周期校验检出。
