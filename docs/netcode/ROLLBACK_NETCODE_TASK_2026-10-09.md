## 2. 关于 SHA-256（澄清）

- SHA-256 是一种“内容指纹”算法：把任意大小的数据算成固定 64 位十六进制字符串，数据有任何改动指纹就不同。它**不限制**单位数量、模组数量或联机人数，与“上限”无关；容量上限来自固定大小的表（UnitID 1024–1087、64 个）与原版 10 位协议。
- 现行用途：`online_session.fingerprint()` 用它把内容清单压成一个指纹，握手时比较，不一致即拒绝连接。
- AGENTS 第 12.1 节停用的是**代理在验证工作中**计算 SHA-256（文件哈希核验），与游戏内功能无关。
- 新模式建议：
  - **匹配时的内容比对**：按模组任务书第 4.6 节的“内容清单”逐项比较（模组 id、版本、覆盖字段、行为库版本），每项可用 SHA-256 或其他摘要；有差异时报告具体项目。
  - **战斗中的同步校验**：每帧或每 N 帧对战斗状态计算轻量校验值（如 CRC32 / xxHash），双方比较以发现不同步；不需要每帧用 SHA-256。

## 3. 为什么选择 Rollback，以及它对本项目的要求

Rollback（以 GGPO 为代表）：双方只交换玩家输入；本地不等待对方，先用“预测输入”（通常沿用对方上一帧输入）继续运行；对方真实输入到达后，若与预测不同，则把游戏状态回滚到该帧，用真实输入重新模拟到当前帧。体验上本地操作零延迟，网络波动只表现为少量画面修正。

本游戏的玩家输入是离散命令（出兵槽位、绝招、AP 升级、弹头车、暂停），频率低，预测命中率高，适合 Rollback。前提条件：

1. **确定性**：同样的初始状态 + 同样的输入序列，两台机器每帧结果逐字节相同。
2. **状态保存/恢复**：能在每帧保存战斗完整状态，并在回滚时快速恢复。
3. **重模拟无副作用**：重新模拟的帧不能重复播放声音、重复创建绘制任务或写存档。
4. **重模拟够快**：一帧显示时间（30 Hz 为 33.3 ms）内需完成“恢复 + 重算若干帧 + 正常一帧”。

## 4. 现状对照（2026-10-09 核查，核心 r31）

| 要求 | 现状 | 风险与待查 |
| --- | --- | --- |
| 确定性 | 游戏逻辑在预编译 x64 DLL 中运行；构建参数含 `-O2 -ffp-contract=off -fno-strict-aliasing`（`src/build.py`），无 fast-math，浮点运算顺序固定，两台机器使用同一 DLL 时有望一致。随机数：原版 `rand()` 位于核心内部；`lrand48/srand48` 由宿主实现（`probe.py` 约 715 行），状态在宿主。 | 宿主时钟（`time/clock_gettime/clock`）是否影响战斗逻辑；宿主随机或 LAB AI（`lab.py` 的段位随机）是否参与战斗；Python 侧状态（EVENT/LAB 钩子、社区内容钩子）是否读写战斗数据；不同 CPU 的数学库（`sin/cos` 已绑定核心实现）结果是否一致。需实测。 |
| 状态保存/恢复 | 战斗状态全部位于客体内存窗口（256 MiB，堆 `0x12000000–0x1e000000`）；圣诞战斗 20 秒时堆高水位 40.6 MiB、存活 29.5 MiB（AGENTS 第 87 节实测）。宿主侧另有分配器表（`probe.allocations/free_blocks`）、句柄、音频与 GPU 资源。 | 每帧完整复制 30–40 MiB 约需 1 GB/s 量级内存带宽，可行但偏重；应评估“只保存战斗相关区域”或“脏页跟踪 + 增量快照”。GPU 纹理与音频不随战斗状态回滚，需保证重模拟不创建/释放这些资源，或以引用计数处理。 |
| 重模拟无副作用 | 原生战斗更新与绘制提交在同一游戏线程同步进行（`player.py` / `probe.step_frame`）。 | 需要把“逻辑更新”与“绘制/音效提交”分离：重模拟帧跳过绘制、静音音效请求（LAB 已有音效端口与通道钩子可借鉴，AGENTS 第 61、62 节）。 |
| 重模拟速度 | 菜单稳态每帧 2–3 ms（高配，第 78 节）；战斗逻辑单帧耗时未单独测量。 | 需测 40/80 单位战斗的纯逻辑帧耗时，决定最大回滚帧数（例如 8 帧 ≈ 267 ms 网络往返）。低配设备另测。 |
| 输入模型 | LAB 本地双人对战已能在同一进程内驱动双方（键盘、手柄，AGENTS 第 71、72 节），命令集合明确。 | 镜头移动属本地视图，不进入同步输入。 |
| 网络层 | 现有 TCP/TLS 转发接口；无 UDP、无局域网发现、无 NAT 穿透。 | Rollback 通常使用 UDP；远程需中继服务器或 NAT 穿透；局域网需广播发现。 |

## 5. 分阶段任务

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| N0 确定性审计 | 同一进程内连续两次、以及两个独立进程，在相同初始存档、相同种子、相同输入序列下运行同一场 LAB 对战，逐帧计算战斗状态校验值并比较；找出所有不一致来源（宿主随机、时钟、Python 状态、未初始化内存等）并修复。 | 1 万帧以上两进程校验值完全一致；不同 CPU 机器（至少 Intel 与 AMD 各一）交叉一致。 |
| N1 快照与恢复 | 实现战斗状态保存/恢复（客体内存相关区域 + 宿主分配器与必要宿主状态）；测量快照大小与耗时，选择完整复制或增量方案。 | 任意帧保存后继续运行 N 帧，再恢复并以相同输入重跑，结果与原运行逐帧一致。 |
| N2 逻辑/表现分离 | 重模拟帧不绘制、不出声、不写存档、不触发 UI 任务；确认纹理与音频资源不因回滚泄漏或重复释放。 | 回滚 8 帧压力测试 10 分钟，无资源增长、无声画异常。 |
| N3 本地 Rollback 模拟 | 在单机上用两个输入源和人工延迟/丢包模拟器运行 Rollback，验证预测、回滚、重模拟与校验。 | 0–200 ms 延迟、0–5% 丢包下帧率稳定，校验无分歧。 |
| N4 网络层 | UDP 传输、输入重发与确认、帧提前量调节、断线检测与重连；局域网广播发现与直连；远程以社区自建的会合服务交换地址后 UDP 打洞直连（无法打洞时提示无法连接，不提供中继）；大厅/会合/内容比对可基于保留的旧接口。 | 局域网两机与远程两机完整对战；断线后可恢复或体面结束。 |
| N5 内容比对与反作弊基础 | 匹配前比对内容清单（含覆盖型模组）；战斗中周期校验分歧时终止并记录。 | 内容不一致必定拒绝匹配并显示差异；人为篡改数值被检测。 |
| N5.5 回放与观战 | 回放文件格式（版本、内容清单、初始条件、输入流、周期校验值）；本地对战与联机对战均可保存回放；回放播放器（暂停、快进、跳转依赖周期快照）；观战者从主机或会合服务接收延迟输入流。 | 回放重放与原对战逐帧校验一致；内容清单不符的回放拒绝播放并提示差异；观战在双方网络正常时持续同步。 |
| N6 产品化 | 联机菜单（主菜单“對戰”页的“局域网/远程”卡片已有占位，AGENTS 第 71–75 节）、房间、准备界面复用 LAB/双人对战准备界面、网络状态显示、设置项（输入延迟帧数）。 | 用户审定。 |

建议顺序：N0、N1 可在性能优化期间先行研究（只读与隔离测试），因为它们决定架构可行性；N2 以后在 M1–M3 完成后实施。
