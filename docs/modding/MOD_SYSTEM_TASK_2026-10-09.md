## 1. 项目总目标（2026-10-09 用户明确）

让玩家可以非常轻松地自由添加自制单位、关卡、地图、EVENT 等内容；玩家在游戏标题主界面（METAL SLUG DEFENSE 标题画面，场景 20，不是主菜单）的 OPTION 中自由选择当前启用的模组；联机时检测双方内容，客户端与服务端的数值类型或单位内容不一致即拒绝匹配；最终形成一个完全开源、高度自定义的游戏版本。

内容分类：

| 类别 | 来源 | 启用方式 | 示例 |
| --- | --- | --- | --- |
| 原版内容 | Android 1.46.0 | 始终启用 | UnitID 1–399、原版世界 |
| 正式版本体内容 | 本项目作者（用户） | 始终启用，不可停用，随版本发布 | 现有 17 款可选社区单位、10 项历史 EVENT、LAB、后续用户新增内容 |
| 模组 | 其他人 | 标题 OPTION 的 MOD 页启用/停用 | 第三方单位、关卡、地图、EVENT |

本体内容与模组使用同一套数据格式、单位容量与行为库；区别只在于来源目录、是否可停用以及联机清单中的标识方式。

## 3. 设计原则

1. **数据优先**：模组只含数据与资源（JSON、OBM/PNG、MSDF/OGG），不执行任意代码（不支持 Python 脚本模组）。
2. **C++ 行为库**：所有特殊行为由游戏本体以 C++ 实现并编入核心，每个行为有稳定名称、版本、参数表与说明。本体内容与模组都通过数据组合调用；新增行为属于游戏本体更新（重建核心），由项目作者完成。
3. **稳定键与动态 ID**：所有内容以稳定键标识（本体使用 `s1xlv.` 前缀，模组使用作者前缀）。运行时 UnitID、图片索引、图标位置由加载器按已安装内容分配；本体内容的分配固定且向后兼容，模组的“键→ID”映射持久化于用户目录，同一模组跨启动不变。
4. **存档安全**：停用模组不删除其进度；停用内容在内存中隐藏，重新启用后恢复。本体内容不可停用，其进度规则不变。
5. **原版与本体不受模组影响**：未启用任何模组时，游戏即为正式版本体；任一模组校验失败只跳过该模组。
6. **开源边界**：项目代码与玩家自制内容可完全开源；原版程序、美术、音乐权利属于原权利人，不随模组重新授权。模组只包含作者有权分发的资源，引用原版资源以 ID/文件名引用。见 `NOTICE.md`、`licenses/`。

## 4. 目标架构

### 4.1 单位容量重构（必须项，优先实施）

目标：单位数量由内容决定，不受 64 个固定槽限制。容量目标（用户确认）：新增单位 4096 个（本体与模组合计），UnitID 1024–5119；设计上不应把 4096 再写成新的不可扩展常量。

需要同时处理的边界（依据契约与现行代码）：

1. **UnitID 空间**：保留原版 0–399 与 UID 0 空槽语义；新增单位从 1024 起按需分配，取消 1087 上限；核查原生所有以 UnitID 为下标的数组与“最大 UnitID+1”缓存（状态行、动作行、商店/主菜单缓存、敌军名单路径、EVENT/LAB 引用）。
2. **精灵描述符与 ImageIndex**：原版 0–422；新增描述符表需可扩展（当前 `423+i`，表位于 `0x10922f28` 的 423×8 字节原表之外的扩展区）；`BattleSpriteFactory` 栈与缓存上限同步扩展。
3. **图标**：现行固定写入 `unit_icon_02.obm` 的 `340+i` 位置，图集面积有限。改为可分页的图标图集（多张图标页或运行时合成），图标位置由加载器分配。
4. **紧凑列表**：拥有单位列表 512 个 int32 槽；需扩容或改为可变长度，并保证原生遍历与排序代码的正确性。
5. **存档**：原生 `test.dat` 的单位记录容量固定（原版 ID）；新增单位进度继续按稳定键存于社区进度文件。核查编队（3 组 × 10 槽，存 UnitID）在 ID 变大后的读写与迁移。
6. **网络协议**：联机单位标识使用稳定键或宽整数，不使用旧 10 位协议。
7. **注册与内容组织**：单一 `registry.json` 拆分为每单位或每内容包的独立文件（本体位于固定目录，模组位于 `mods/`），由加载器合并；保留现有 20 条记录的稳定键、ID 与玩家进度（迁移须零变化）。
8. **性能**：单位数量增长不应线性增加启动时间；描述符、图集与图标按需加载（与性能任务书的预加载设计协调）。
9. **客体内存窗口**：核心保留原版 ARM 32 位数据模型（寄存器与游戏数据结构中的指针均为 32 位），客体地址窗口为 `0x10000000` 起 256 MiB（`probe.py` 的 `BASE, SIZE`、`static_cpu.py` 的布局检查），堆为 `0x12000000–0x1e000000`（192 MiB）。2026-10-09 实测（`verification/event_fixes_20261009/measure_heap.py`，隔离存档）：启动后高水位 15.6 MiB，EVENT 基地 20.6 MiB，圣诞战斗 20 秒 40.6 MiB（存活 29.5 MiB）。单位元数据很小（状态数据行 0x390 字节/单位，1 万个约 9 MiB），故容量瓶颈在固定表而非内存；图集须按需加载、战斗外释放。若后续确需更大窗口，可在 32 位地址范围内重新布局（需同步核心中的固定地址，如各 LAB/EVENT 头部 `0x1ffe....`、线程栈与 STOP 地址），属于独立任务。

验收：现有 17+3 条记录迁移后，40 等级参数、商店、编队、拥有状态、战斗表现与存档重启逐项一致；以生成的测试单位（例如 500、2000 个）验证注册、商店列表、强化列表、编队、战斗出击、敌军名单与重启；原版 400 条数据行回归不变。

### 4.2 C++ 行为库

- 把现有专用适配整理为通用行为，每项具备：稳定名称（如 `flame_burst_interruptible`、`summon_on_build`、`insect_swarm_release`、`para_drop_transform`、`retained_special_weapon`、`single_knockback_per_special`）、版本、参数 schema（类型、范围、默认值）、作用的动作槽与状态、依赖的资源约定、说明与示例。
- 单位数据以列表形式组合行为，例如 `"behaviors": [{"name": "flame_burst_interruptible", "version": 1, "params": {...}}]`；加载器校验参数并写入核心的行为参数表（核心按单位查询，替代现行按具体单位写定的分支）。
- 现有本体单位（KT-21、白/绿木乃伊、木乃伊召唤箱 MKII、正规军伞兵/迫击炮兵、保留武器角色等）作为每个行为的回归基准：迁移到行为库后参数与画面一致。
- 原版单位的动作类与攻击模式本身也是可复用的“基础行为”（现行 `base_id` 克隆与动作/弹体参考字段），在文档中列为可用清单。
- 行为库清单与参数说明写入作者指南，联机内容清单记录所用行为及版本。

### 4.3 模组包格式（拟议）

```
mods/
  author.mod_name/
    mod.json            # 清单
    units/*.json        # 单位（不写定 id；含 behaviors 组合）
    campaign/*.json     # 世界/区域/关卡（沿用 catalog schema 1）
    events/*.json       # 自制 EVENT（待定义）
    assets/             # OBM/PNG、MSDF/OGG、图标
    localization/*.json # 文本
    LICENSE
```

`mod.json` 字段（草案）：`id`、`name`（多语言）、`version`、`author`、`license`、`game_version`（兼容范围）、`schema`、`depends`/`conflicts`、`load_order`、`content`、`behaviors_required`（所需行为及最低版本）。本体内容使用同一内容格式，但存放于本体目录、无 `mod.json` 启停项。

### 4.4 加载流程

启动 → 加载本体内容 → 读取 `mods/` 与启用列表（用户目录 `mods_enabled.json`，不放入存档目录）→ 校验清单、依赖、冲突、版本、行为可用性、容量 → 合并 → 分配/恢复 ID → 安装进原生 → 生成内容清单。校验失败的模组整体跳过并在 MOD 页显示原因。

### 4.5 标题 OPTION 的 MOD 页

- 标题画面（场景 20）原生 OPTION 中新增“MOD”入口，使用原生素材与音效。
- 列表（名称、作者、版本、内容类型、状态）、启用/停用、加载顺序、详情（描述、许可、依赖、所需行为、校验错误）、“全部停用”。
- 生效时机（用户确认）：启用或停用模组后**重启游戏生效**；运行中不卸载或重装已安装内容，以免性能损失。MOD 页保存选择并提示重启。
- 界面文字跟随游戏语言。

### 4.6 联机内容检测

- 清单内容：游戏版本、核心版本、行为库版本、本体内容版本，以及每个启用模组的 id、版本与内容摘要；单位与关卡参数按规范化数值比较。
- 任一差异即拒绝匹配，并返回差异说明（缺少模组、版本不同、数值不同、行为版本不同）。
- AGENTS 第 12.1 节停用的是代理验证中的 SHA-256；联机内容摘要属于游戏功能（现行 `fingerprint` 使用 SHA-256），实施前与用户确认算法。
- 服务端裁决、防篡改与反作弊另行设计。

### 4.6.1 联机开发方向（用户确认为重要方向）

- 时机：性能优化（`docs/performance/PERFORMANCE_AND_PRELOAD_TASK_2026-10-09.md`）与 M1–M3 重构完成后，作为重要开发方向推进。期间所有重构不得破坏联机前提：确定性战斗、稳定键标识、内容清单可比对。
- 目标：远程联机（自有服务器，基于 `online_session.py` / `room_server.py` 已实现的 TCP/TLS 房间、认证、内容指纹与输入帧契约，AGENTS 第 18 节）与局域网联机（局域网发现与直连；可复用同一协议，一方做主机）。
- 战斗基础：本地双人对战（LAB 双人模式，AGENTS 第 71、72 节）已在同一进程内驱动双方；联机需要在两台机器之间同步输入帧与状态校验，处理延迟、纠偏与断线重连（第 18 节列为待开发）。
- 原版 Wi-Fi 的 10 位 UID 协议不能表达新单位，联机协议以稳定键或宽整数标识单位。
- 覆盖型模组会改变战斗数值，必须进入内容清单比对（第 4.8 节）。

### 4.7 作者工具

`content_tool.py` 扩展：`new-mod`、`validate`（逐项错误与位置）、`pack`、`import-png`/`import-music`、`list-behaviors`（输出行为库清单与参数说明）、`preview`（隔离存档启动预览）。`docs/CONTENT_AUTHORING.md` 改写为中英双语作者指南，附最小单位、最小关卡、最小 EVENT 模板模组。

### 4.8 覆盖型模组（修改原版或本体数值）

- 用户确认模组可以修改原版游戏数值。覆盖以“补丁”形式声明：目标稳定键或原版 UnitID/关卡 ID、字段路径、新值；不复制整条记录。
- 加载顺序决定冲突结果：同一字段被多个模组修改时，后加载者生效，MOD 页显示冲突提示。
- 覆盖只在加载时作用于内存中的运行表，不写入原版数据文件与存档；停用模组并重启后恢复原值。
- 覆盖的字段集合与平衡规则（AGENTS 第 6.1 节的联动规则，如生命值与击退门槛）在作者指南中说明，校验器对越界或类型错误给出提示。
- 联机：所有覆盖计入内容清单，双方覆盖不一致即拒绝匹配。

## 10. 待办：击退门槛绝对值、Lv41–50 与高强度关卡（2026-10-10 登记）

### 10.1 击退门槛绝对值字段（宿主，不改核心）

- 原生语义（生成代码 `BattleUnit::damage` 0x101e0a4c、`BattleUnitDefault::damageAction` 0x1016f484 核实）：计量上限 = 状态词 4 × 100；每次受击扣除攻击方击退力；`damageAction` 在计量 ≤0 时预约状态 80（击退）；上限 >0 时才回填计量。门槛 -1 的单位上限为 -100，永不回填，因而**每次受击都击退**；处于原生“霸体”标志（位 128）期间计量钳为 1，不击退。
- 原版 400 行中 391 行的门槛六个锚点相同，8 行随等级变化。
- 需求：玩家/模组可把 -1 单位改为有门槛，或反向改为 -1，或设很大的门槛（基本不可击退）。-1 单位本来每次受击都进入状态 80，已有击退动作，无需占位精灵。
- 方案：新增绝对值字段（例如 `knockback_threshold`：整数，或六锚点数组），允许 -1；可用于本体单位、模组单位和模组对原版单位的补丁（补丁字段白名单相应扩大），计入联机内容清单。与 `knockback_threshold_multiplier` 同时出现时拒绝。

### 10.2 Lv41–50（核心改动）

- **插值**：`StatusLevelUpParam(f,i,f,i,f,i,f,i,f,i,f,i)`（0x1ce47a）以内部等级 lv（0 = Lv1）在 Lv1/10/20/30/40 五个锚点间分段插值；lv ≥39 一律返回 Lv40 锚点，第 6 组参数（Lv50 锚点及其插值类型）被传入但从不读取。各段插值类型取该段的类型字：0 为二次缓入（x²），1 为线性，2 为二次缓出（1−(1−x)²）。延伸方法：钩住该函数，lv 40–48 在 Lv40→Lv50 锚点间按第 6 组类型字同样插值，lv 49 取 Lv50 锚点。所有经该函数插值的状态（生命、伤害、射程等）共用这一点。
- **原版 Lv50 数据可直接使用**：数据行每个锚点块第 33 个字为该段插值类型（原版 279 行为线性、61 行缓入、41 行缓出）。生命值有 348 行的 Lv50 锚点不同于 Lv40，且全部与 Lv30→40 的步长相同（例如基寇卡 4200→4900）；普攻伤害 293 行、绝招伤害 287 行同样等步长；其余行 Lv50 等于 Lv40；再出击间隔全部相同。即原版已按既有趋势填好 Lv50，开放后无需重新制作原版单位数值。社区单位的倍率与补丁已作用于全部六个锚点。
- **存档等级字段**：原版单位等级为 int16（UnitID <300 与 ≥300 各一组数组），宽度足够；`GetUnitLevelSaveData` 与 `AddUnitLevelSaveData` 把值钳到 40（内部值），需一并钩住放宽到 49。社区单位等级存于社区进度 JSON，无宽度限制。
- **上限与开放**：原生突破函数与我方等级规则钩子（`src/unit_level_rules.inc`）按 35/40 设计，需扩展到 50；开放条件照搬 30/35/40 的阶段交易（核心道具、MSP/勋章），具体条件由用户定。强化 MSP 费用按 Lv1–40 的趋势外推（费用函数位置待定位）。界面等级显示、商店/强化/编队的上限判断需逐项核查。
- **敌军**：敌军以“配置等级 − 1”调用同一插值，现有配置为 41–50 的记录目前都按 Lv40 计算（第 16 节：里地图 3 有 127 条 50 级）。开放插值前，先把原版关卡中 41–50 的配置改回 40（数据修改，现行数值不变）；之后自制关卡可使用真正的 Lv41–50。

### 10.3 关卡强化倍率（宿主为主）

- 原生关卡强化为“生命/攻击 × (1 + 0.2 × 强化参数)”，原版最高参数 5（2 倍）。实际作用值为每队两个浮点数（`BattleObjectManager+72` 起，生命、攻击），LAB 优势设定已直接写入该浮点（第 49 节），说明可设任意倍率。
