# M1b：多页单位图标与 500–4096 个测试单位验证（2026-10-10）

依据：`MOD_SYSTEM_TASK_2026-10-09.md`、`M0_SPEC_AND_BOUNDARIES_2026-10-09.md`（第 1 节第 7、8、11、12 项）、`M1A_REGISTRY_SPLIT_2026-10-10.md`。核心 r35 → **r36**（`MSD_Core_LAB_r36_20261010.dll`）。

## 1. 多页单位图标

### 1.1 内容格式

- 原有写法 `"icon": {"page": 1, "rect": [...], "anchor": [...]}` 继续表示 `unit_icon_02.obm` 中的图标。
- 新写法 `"icon": {"atlas": "<图集>.obm", "rect": [...], "anchor": [...]}` 表示图标位于该图集（须登记在 `content.json` 的 `assets`）。加载器按图集首次出现顺序（UnitID 升序）分配页号 2、3…，并写入内存清单的 `icon.page`。两种写法不能同时出现。
- 图集为 OBM（建议 RGBA32，1024×1024，可放 256 个 64×64 格）。矩形须在图集范围内。

### 1.2 原生依据（静态反汇编核实）

- 菜单：任务绘制共用 `GraphicsOpt::drawConv(Image**, …, const C_CONV*, …)`（0x136b14），按矩形 +0xe 的页号取 `images[page]`。`drawPict` 三个重载、`GT_NormalDraw`、`NormalDraw` 三个重载、`GT_CommonDraw` 都经此入口。各场景把 `unit_icon_01/02` 载入不同的菜单图像槽（主菜单 33/34，编队 25/26），所以不能按基址判断。
- 战斗出兵格：`BattlePlayerOperator::createGrahics` 以 `ImageName_UnitIcon`（`unit_icon_02.obm`）读入一张 CPU 图（`ImageDesc`），按 UnitID 取矩形逐格复制（`imageCopy`、`imageCopyGrayscale`，源图在 fp）。页号字段不参与。

### 1.3 实现

- 头部新增字段：+120 页表、+124 页数、+128 扩展 `ConvUnitIcon` 地址、+132 战斗共用页 `ImageDesc`、+136 其中当前载入的页号。每页 16 字节：文件名、菜单纹理 `Image*`、保留、标记（位 0 为菜单请求）。无图标页时全部为 0，原有行为不变。
- 菜单钩子（0x10136b15）：矩形落在扩展 `ConvUnitIcon` 的社区段且页号 ≥2 时，把基址改到页表，使 `images[page]` 取得该页纹理；纹理未创建时登记请求并跳过本次绘制。宿主 `CommunityContent.sync_icon_pages`（每帧 `flush` 中）在下一帧前用 `Image::createImage` 创建纹理，场景切换时释放（原生菜单图像同样按场景载入与释放）。
- 战斗钩子（块 0x101dacbc）：页号 ≥2 的社区单位把源图改为共用页 `ImageDesc`。所需页未载入时，由原生代码调用 `ImageDesc::readFileFromOBM`（返回循环头 0x101dacaa 重新取同一格，循环头只依赖被调用者保存的寄存器）；`create` 会先释放上一页像素，所以同一时刻只占一页内存。宿主在下一帧释放该 `ImageDesc`。文件读取需要宿主处理文件导入，所以采用正常执行流程中的调用，而不是 C++ 内嵌套调用。
- LAB 准备界面的宿主自绘头像（`lab_ui.Skin`）支持 `icon.atlas`，并优先使用加载器已读入的图集字节。
- 核心导出 `msd_community_icon_pages_version()==1`；内容使用图标页时，加载器检查核心是否支持。

## 2. 单位数量较多时的原生缓冲区修正（r36）

批量测试中发现以下固定容量，均已改为按实际数量：

| 位置 | 原状态 | 问题 | r36 |
| --- | --- | --- | --- |
| `CreateUnitListCustum` 社区覆盖块（强化列表） | 栈上暂存表 2048 字节（512 个），清零与复制 2048 字节 | 已拥有单位超过 512 个时写出栈缓冲区 | 栈表、清零、复制长度为列表容量（头部 +40）×4 |
| `InitDeckPanels` 社区覆盖块（编队面板） | 栈帧 2108（局部 56 + 表 2048 + 4），复制循环 2048 字节 | 同上 | 栈帧 56 + 容量×4 + 4，复制长度同上 |
| `BattleSpriteFactory::releaseUnusedResourcesAll` 社区覆盖块 | 栈帧固定 516 字节（按 64 个社区单位），清零与标记范围为图片总数 | 槽位多于约 93 个时，退出场景（`SceneEndFunc`）写出栈缓冲区，返回地址被破坏（实测 500 个测试单位时主菜单退出崩溃） | 栈帧 max(516, 不小于图片总数且 ≡4 mod 8) |

宿主把列表容量取为 8 的倍数（`max(512, 400+槽位数)` 向上取整），以保持原生栈帧 8 字节对齐。本体现有内容（20 个槽位）下以上长度与 r35 相同。

## 3. 验证（`verification/m1b_20261010/`，隔离存档，未写入任何个人存档，未计算 SHA-256）

- 测试内容：`make_test_content.py` 复制本体内容并追加 N 个测试单位（以正规军步枪兵为模板，UnitID 2048 起，1044–2047 为占位槽位；AP、价格、阵营按序号变化；头像为编号图标，排入 1024×1024 图标页）。驱动 `run_scale.py`，汇总 `summary.json`。
- 500 / 2000 / 4096 个测试单位各 10 项检查全部通过：安装（槽位 1524 / 3024 / 5120，图标页 2 / 8 / 16，组合包商店 ID 2036 / 3536 / 5632）；单位目录；单位商店；强化列表（拥有 666 / 1416 / 2464 个，原生重新排序成员不变）；编队面板（667 / 1417 / 2465 个，原生重新排序）；跳到含测试单位的编队页，图标页纹理按需创建并正确显示；LAB 准备界面与战斗出兵格显示测试单位头像；双方 AI 出兵（敌我两侧均出现测试单位）。
- 重启：4096 个单位的存档重新启动后，2048 个已拥有测试单位的拥有状态与等级保持，其余检查同样通过。
- 本体内容回归（无测试单位）：r36 与 r35 各 10 项检查结果相同（强化列表 413、编队 414、LAB 出兵单位相同）。七张截图中六张逐像素相同，另一张只在 AP 数字框处不同（AP 数值受以时间为种子的随机数影响）。M1a 的安装一致性、默认 11 项与空位场景 10 项在 r36 上全部通过。
- 时间与内存（4096 个单位，最终构建）：加载器读取 4116 个单位文件 0.85 秒（首次读取新写入的文件时约 24 秒，属操作系统冷读取）；`initialize`（含原生安装）1.8 秒；单位目录索引 183 ms，按综合强度排序全部 4491 条 135 ms，其余筛选 1 ms 以内；进入商店 144 ms、强化 209 ms（重新排序 127 ms）、编队 142 ms；工作集 684 → 965 MiB；客体堆高水位 LAB 战斗时 69 MiB（192 MiB 窗口），500 个单位时 58 MiB。改为共用页 `ImageDesc` 前为 117 MiB。测试机为 i9-13900HX，低配设备未测。
